# Architecture decisions

One entry per decision. This feeds the README's "Architecture decisions" section and doubles as interview prep.

| # | Decision | Why | Trade-off accepted |
|---|---|---|---|
| 1 | Node.js + Express for the mock backend | The assignment names it as preferred; no deviation to justify | Less familiar than Python, but less code to explain |
| 2 | Bloc for state management | Sealed states give exhaustive compile-time checking; `BlocSelector` gives precise rebuild control; `droppable()` solves duplicate submit declaratively | More boilerplate than Riverpod |
| 3 | Backend is the only owner of wallet balance | Explicit business rule in the spec; also the correct real-world design | Extra round trip after a transfer |
| 4 | Idempotency key generated when the confirmation screen opens | Lets a timeout retry reuse the same key, so a retry cannot double-deduct | Key must be cleared when a new transfer starts |
| 5 | No automatic retry interceptor | An auto-retry on a transfer endpoint risks silent double submission; retry is user-initiated and keyed | Slightly worse UX on flaky networks |
| 6 | Search and Credit/Debit filter applied client-side | The spec's list endpoint has no query params; the dataset is small | Would not scale past a few hundred rows; noted as a limitation |
| 7 | In-memory backend store, single process | Spec allows in-memory; keeps the check-and-deduct atomic without a database | State resets on restart; documented |

| 8 | Section-level shimmer instead of a full-screen loader | Balance and transactions come from separate endpoints and separate blocs, so each resolves on its own; it also proves the rebuild scope is isolated | More widgets to build and test |
| 9 | Shimmer for fetching, button spinner for actions | One loading vocabulary per kind of wait, so the UI never shows two at once | None |
| 10 | Bundle static TTFs (Space Mono, Sora, Manrope) as assets; dropped `google_fonts` | Runtime font fetching hits the network in `flutter test` and on first launch; bundled fonts are deterministic and work offline | ~540 KB of font files in the APK |
| 11 | Letter spacing written as `em * fontSize` in `app_text_styles.dart` | DESIGN.md gives `em`; Flutter takes logical pixels; keeping the multiplication visible makes each value traceable to the spec | None |
| 12 | Fake repositories with sample values during the UI slices, each file marked TEMPORARY | Lets the seven screens be built and tested before networking exists; they are Dart stubs, not JSON, and are deleted when the data slice lands so NFR-01 holds in the final app | Must remember to delete them; the header makes them greppable |
| 13 | Hex literals allowed in `test/theme_test.dart` | The test exists to pin the token values from DESIGN.md, so it has to state them; the no-hex rule applies to `lib/` | None |
| 14 | Design tokens live in `core/theme`; one-off component geometry (a 9px dot, an 84px tile) is a named constant in that component's file | The component is the only user, so it is the single source; moving every number into `AppSpacing` would bury the tokens | Two places to look for sizes |
| 15 | Shimmer placeholders sit in slots one real text line tall, measured with `TextPainter` | The engine rounds line heights (16.8 renders as 17), so arithmetic drifted; measuring matches the real `Text` exactly, at any text scale, so nothing jumps on load | Gaps between placeholder bars follow the real layout, not the shimmer gaps in DESIGN.md (e.g. 7px), which would have caused a jump |
| 16 | `TransactionRail` and `DetailCard` use a shrink-wrapped, non-scrolling `ListView` inside the screen's scroll view | Satisfies "lists use ListView.builder" while letting a short list sit inside a page; History will use an outer `ListView.builder` over day groups | Shrink-wrapped lists build every row; fine for the dozens of rows here |
| 17 | `BalancePanel`, `QuickActionCard`, `FilterPill`, `AmountField` stay in `core/widgets` although each serves one screen | UI-TASKS T1 lists them there explicitly, which overrides its own "single-screen widgets belong to the screen" check | Revisit if the critic pass prefers moving them |
| 18 | DESIGN.md's `TransactionSkeleton` not built | `TransactionRowShimmer` covers the same job and is the one UI-TASKS asks for; two placeholders for one row would be duplication | None |
| 19 | Back chevron and quick-action icons are Material icons | No icon package needed; Material icons have no stroke-width control, so DESIGN's 1.7/1.8 stroke is approximate | Slightly heavier glyphs than the mock |
| 20 | Router takes a `ValueListenable<bool> isAuthenticated` instead of reading a stub auth class | One input serves as both the guard's flag and `refreshListenable`; tests pass a `ValueNotifier`, and the auth slice passes one driven by `AuthBloc` without touching the router | A thin adapter from `AuthBloc` to a listenable is needed later |
| 21 | Guard written as a pure `authRedirect` function | The whole rule fits in four lines and can be read without go_router knowledge | None |
| 22 | Routes render a TEMPORARY `RoutePlaceholder` until T3–T9 swap in each screen | T2 is routing only; placeholders let every route be tested now | Each screen task edits one builder in `app_router.dart` |
| 23 | `initialLocation` is `/dashboard`; the guard sends signed-out users to `/login` | A signed-in start lands on the dashboard with no flicker through login | None |
| 24 | Login validators written as real domain code, not TEMPORARY stubs | They are pure functions graded by TST-01 and will not change when the data slice lands | None |
| 25 | Login footer pinned below a scrolling form, not pushed down by a spacer inside the scroll view | Spacer-in-scroll needs intrinsic heights, which text fields report wrongly (it overflowed); a pinned footer needs none | The footer stays visible above the keyboard |
| 26 | Login API error shown as a brand caption under the password field | DESIGN.md does not place it; keeping it beside the fields keeps the form readable and matches the field-error style | None |
| 27 | The `/login` route passes a no-op `onSubmit` until the auth slice | T3 is presentation only; the screen reports a valid submission and the caller decides what happens | Sign in does nothing when the app is run before the auth slice |
| 28 | A sealed `Section<T>` (loading / loaded / failed) per independently-loading part of a screen | One small type gives every section the same three states and an exhaustive `switch`, so balance and activity can be in different states at once | A bloc's state has to be mapped into sections by whoever builds the screen |
| 29 | Dashboard sections default to `SectionLoading`; the screen holds no sample data | Renders standalone without fake balances or transactions in the widget tree (NFR-01); tests pass their own values | Running the app before the data slice shows shimmer forever |
| 30 | "See all" row is 44px tall for its touch target; the gaps around it shrink by the same amount | Keeps the visual spacing DESIGN.md gives while meeting the 44px minimum | Gap constants differ from the DESIGN numbers, with a comment saying why |
| 31 | Dashboard caps recent activity at five rows via `itemCount`, not by trimming the list in `build` | The cap is a layout fact, not data logic; no list is copied or filtered in `build` | None |
| 32 | Router tests pump past transitions instead of `pumpAndSettle` | The dashboard's shimmer animates until data arrives, so the tree never settles | None |
| 33 | Transfer validators are real domain code mirroring backend API-06, with no balance check | They are graded by TST-02; the client must not pre-reject for insufficient balance (TRF-08), so the 409 path stays testable | A user can submit an amount the backend will reject |
| 34 | The amount must be plain digits with an optional dot (no commas, sign or exponent) | Matches what the backend accepts and keeps the rule to one regex; `double.tryParse` alone would accept `1e3` | Typing `1,500` shows an error; the reference screenshot shows grouped digits |
| 35 | Send money hands back a `TransferDraft` of trimmed strings, remarks null when empty | Turning text into a number for the request belongs to the data layer; the screen stays formatting-free | Conversion happens later, in one place |
| 36 | Phone-kind text fields type in Space Mono (`monoInput`) | DESIGN.md's rule puts phone numbers in mono, and the reference shows mono digits | One-line change to the T1 text field |
| 37 | Pushed screens go back with `canPop ? pop : go(dashboard)` | A screen opened directly (no history) would otherwise have nothing to pop | None |
| 38 | Confirmation's BALANCE AFTER row is optional, only ever a backend-supplied value, and hidden when absent | The mock shows it, but filling it means computing `available - amount` in the app, which rule 1 forbids; the backend has no preview endpoint | The row is not shown until the backend offers one |
| 39 | Request key shown in full on confirmation (the mock shortens it) | It is the Idempotency-Key; showing it whole lets it be matched against backend logs in the demo | Small mono text, ellipsised on narrow screens |
| 40 | Confirmation is stateless: Confirm is disabled while `isSubmitting`, and Edit, back arrow and system back are inert | One attempt, one request (TRF-05); same-frame double taps are dropped by `droppable()` in TransferBloc, as the skill file pairs them | Relies on the bloc for same-frame taps |
| 41 | `/transfer/confirm` stays a placeholder until TransferBloc exists | Its data is the draft plus a request key the bloc generates; the skill file allows route `extra` only between confirmation and result | The send-money flow dead-ends at a placeholder until the data slice |
| 42 | Result screen takes a sealed `TransferResultView` (succeeded / failed) and switches on it | One screen class for both outcomes, as T7 requires, with the compiler checking both branches | None |
| 43 | Failure subtitle is supplied by the caller; "Your wallet was not debited" is only the default | That sentence is true for a server error (e.g. 409) but not after a timeout, where the outcome is unknown | The caller must pick the right copy per failure type |
| 44 | `DetailCard` gained an optional `header` (the failure banner) | The banner sits inside the card border per DESIGN.md; a header slot keeps one card widget instead of a second card | One extra parameter on a T1 widget |
| 45 | System back on the result screen goes to the dashboard | Going back to confirmation after a finished attempt invites a duplicate send | None |
| 46 | `/transfer/result` receives its outcome via route `extra`; opened directly it shows the placeholder | The skill file allows `extra` only on this hop; there is no id to refetch a result by | A deep link to the result screen shows nothing useful |
| 47 | History sorting, search, filter, grouping and date headers live in one pure function, `groupHistory` | Keeps all logic out of `build`, is unit-tested directly, and TransactionsBloc can call the same function later | None |
| 48 | The screen recomputes groups only when data, query or filter change, and stores the result in state | `build` just renders the stored groups; typing re-filters immediately | No debounce yet; the bloc adds `restartable()`/debounce in the data slice |
| 49 | "No matching transactions" is a separate empty state from "No transactions yet" | TXN-04 requires distinct messages for an empty wallet and an over-narrow filter | None |
| 50 | `TransactionRowData.dateLabel` renamed `metaLabel` | History rows show the type (DEBIT/CREDIT) in that slot, dashboard rows show the date; the old name was wrong for one of them | Touched a T1 widget and two test files |
| 51 | Top bar, search and pills stay fixed; only the grouped list scrolls, via an outer `ListView.builder` over day groups | Search stays reachable on long lists, and the list is lazy at the group level as decision 16 planned | Each day's rail is shrink-wrapped (fine for a day's rows) |
| 52 | Details labels the counterparty BENEFICIARY for a debit and SENDER for a credit | TXN-07 says "beneficiary/sender"; on a credit the other party sent the money | Differs from the single label in the mock |
| 53 | Bordered, clipped containers (`DetailCard`, its shimmer, the text-field frame) paint their border as a `foregroundDecoration` | Found in the T9 render: a border painted behind filled content (white rows, the surface row, the `+91` box) loses its curve at the rounded corners | Content now runs to the card edge; the border overlays its outer pixel |
| 54 | The details hero amount sits in a fixed one-line slot, like the balance panel | `FittedBox` shrinks height along with width for long amounts, which moved the card when details arrived; a test now pins the card's position across loading and loaded | None |
| 55 | The details loading pill is the real pill outline with a shimmering dot and label | A plain shimmer block of a guessed height was 3px off the real pill | None |
| 56 | `main.dart` runs `JWalletApp`: theme plus `MaterialApp.router`, router created once in `initState` | Building the router in `build` would reset navigation on every rebuild | None |
| 57 | Until the auth slice, any login input that passes validation signs in (TEMPORARY, in `main.dart`) | Lets all screens be walked end to end now; `createAppRouter` takes `onLoginSubmitted`, which AuthBloc will own | Credentials are not checked in this interim build |
| 58 | Send money → Confirmation passes a `TransferAttempt` (draft plus request key) as route `extra`; the key is made on the push | The skill file reserves `extra` for confirmation → result, but there is no TransferBloc yet; making the key in the confirm builder would change it on every rebuild (a test pins this) | Second use of `extra`; moves into TransferBloc in the data slice |
| 59 | `ConfirmationView.fromDraft` formats the amount with Indian grouping (`₹1,500.00`) and adds `+91` | One place turns a draft into display values; the amount is parsed only for display | None |
| 60 | Fake repositories feed the screens through one TEMPORARY file, `core/router/temporary_fake_wiring.dart` (`FakeData`, per-screen `Fake*` wrappers, entity-to-view converters) | Lets the whole app be walked with sample data before the backend exists, and keeps every piece of sample-data plumbing in one deletable file | Sample data in the app breaks rule 2 / NFR-01 until the data slice deletes this file and the fake repositories; it must not ship |
| 61 | Fake answers are delayed by differing amounts (profile 0.35s, balance 0.7s, list 1.1s; tests use zero) | Makes shimmer and independent section loading visible in the running app | None |
| 62 | Confirm → result uses `go`, not `push` | The finished attempt leaves the back stack, so back can never return to confirmation and resend | None |
| 63 | The fake transfer result's id now points at an existing fake transaction (TXN10006) | "View transaction" opens real details instead of a not-found error | The fake result is fixed: it always reports ₹1,500.00 and the same balance, whatever amount is entered |
