# Architecture decisions

One entry per decision. This feeds the README's "Architecture decisions" section and doubles as interview prep.

| # | Decision | Why | Trade-off accepted |
|---|---|---|---|
| 1 | Node.js + Express for the mock backend | The assignment names it as preferred; no deviation to justify | Less familiar than Python, but less code to explain |
| 2 | Bloc for state management | Sealed states give exhaustive compile-time checking; `BlocSelector` gives precise rebuild control; `droppable()` solves duplicate submit declaratively | More boilerplate than Riverpod |
| 3 | Backend is the only owner of wallet balance | Explicit business rule in the spec; also the correct real-world design | Extra round trip after a transfer |
| 4 | Idempotency key generated when the confirmation screen opens | Lets a timeout retry reuse the same key, so a retry cannot double-deduct | Key must be cleared when a new transfer starts |
| 5 | No automatic retry interceptor | An auto-retry on a transfer endpoint risks silent double submission; retry is user-initiated and keyed | Slightly worse UX on flaky networks |
| 6 | Search and Credit/Debit filter applied client-side | The spec's list endpoint has no query params; the dataset is small | Would not scale past a few hundred rows; noted as a limitation |
| 7 | In-memory backend store, single process | Spec allows in-memory; keeps the check-and-deduct atomic without a database | State resets on restart; documented |

| 8 | Section-level shimmer instead of a full-screen loader | Balance and transactions come from separate endpoints and separate blocs, so each resolves on its own; it also proves the rebuild scope is isolated | More widgets to build and test |
| 9 | Shimmer for fetching, button spinner for actions | One loading vocabulary per kind of wait, so the UI never shows two at once | None |
| 10 | Bundle static TTFs (Space Mono, Sora, Manrope) as assets; dropped `google_fonts` | Runtime font fetching hits the network in `flutter test` and on first launch; bundled fonts are deterministic and work offline | ~540 KB of font files in the APK |
| 11 | Letter spacing written as `em * fontSize` in `app_text_styles.dart` | DESIGN.md gives `em`; Flutter takes logical pixels; keeping the multiplication visible makes each value traceable to the spec | None |
| 12 | Fake repositories with sample values during the UI slices, each file marked TEMPORARY | Lets the seven screens be built and tested before networking exists; they are Dart stubs, not JSON, and are deleted when the data slice lands so NFR-01 holds in the final app | Must remember to delete them; the header makes them greppable |
| 13 | Hex literals allowed in `test/theme_test.dart` | The test exists to pin the token values from DESIGN.md, so it has to state them; the no-hex rule applies to `lib/` | None |
| 14 | Design tokens live in `core/theme`; one-off component geometry (a 9px dot, an 84px tile) is a named constant in that component's file | The component is the only user, so it is the single source; moving every number into `AppSpacing` would bury the tokens | Two places to look for sizes |
| 15 | Shimmer placeholders sit in slots one real text line tall, measured with `TextPainter` | The engine rounds line heights (16.8 renders as 17), so arithmetic drifted; measuring matches the real `Text` exactly, at any text scale, so nothing jumps on load | Gaps between placeholder bars follow the real layout, not the shimmer gaps in DESIGN.md (e.g. 7px), which would have caused a jump |
| 16 | `TransactionRail` and `DetailCard` use a shrink-wrapped, non-scrolling `ListView` inside the screen's scroll view | Satisfies "lists use ListView.builder" while letting a short list sit inside a page; History will use an outer `ListView.builder` over day groups | Shrink-wrapped lists build every row; fine for the dozens of rows here |
| 17 | `BalancePanel`, `QuickActionCard`, `FilterPill`, `AmountField` stay in `core/widgets` although each serves one screen | UI-TASKS T1 lists them there explicitly, which overrides its own "single-screen widgets belong to the screen" check | Revisit if the critic pass prefers moving them |
| 18 | DESIGN.md's `TransactionSkeleton` not built | `TransactionRowShimmer` covers the same job and is the one UI-TASKS asks for; two placeholders for one row would be duplication | None |
| 19 | Back chevron and quick-action icons are Material icons | No icon package needed; Material icons have no stroke-width control, so DESIGN's 1.7/1.8 stroke is approximate | Slightly heavier glyphs than the mock |
| 20 | Router takes a `ValueListenable<bool> isAuthenticated` instead of reading a stub auth class | One input serves as both the guard's flag and `refreshListenable`; tests pass a `ValueNotifier`, and the auth slice passes one driven by `AuthBloc` without touching the router | A thin adapter from `AuthBloc` to a listenable is needed later |
| 21 | Guard written as a pure `authRedirect` function | The whole rule fits in four lines and can be read without go_router knowledge | None |
| 22 | Routes render a TEMPORARY `RoutePlaceholder` until T3–T9 swap in each screen | T2 is routing only; placeholders let every route be tested now | Each screen task edits one builder in `app_router.dart` |
| 23 | `initialLocation` is `/dashboard`; the guard sends signed-out users to `/login` | A signed-in start lands on the dashboard with no flicker through login | None |
| 24 | Login validators written as real domain code, not TEMPORARY stubs | They are pure functions graded by TST-01 and will not change when the data slice lands | None |
| 25 | Login footer pinned below a scrolling form, not pushed down by a spacer inside the scroll view | Spacer-in-scroll needs intrinsic heights, which text fields report wrongly (it overflowed); a pinned footer needs none | The footer stays visible above the keyboard |
| 26 | Login API error shown as a brand caption under the password field | DESIGN.md does not place it; keeping it beside the fields keeps the form readable and matches the field-error style | None |
| 27 | The `/login` route passes a no-op `onSubmit` until the auth slice | T3 is presentation only; the screen reports a valid submission and the caller decides what happens | Sign in does nothing when the app is run before the auth slice |
| 28 | A sealed `Section<T>` (loading / loaded / failed) per independently-loading part of a screen | One small type gives every section the same three states and an exhaustive `switch`, so balance and activity can be in different states at once | A bloc's state has to be mapped into sections by whoever builds the screen |
| 29 | Dashboard sections default to `SectionLoading`; the screen holds no sample data | Renders standalone without fake balances or transactions in the widget tree (NFR-01); tests pass their own values | Running the app before the data slice shows shimmer forever |
| 30 | "See all" row is 44px tall for its touch target; the gaps around it shrink by the same amount | Keeps the visual spacing DESIGN.md gives while meeting the 44px minimum | Gap constants differ from the DESIGN numbers, with a comment saying why |
| 31 | Dashboard caps recent activity at five rows via `itemCount`, not by trimming the list in `build` | The cap is a layout fact, not data logic; no list is copied or filtered in `build` | None |
| 32 | Router tests pump past transitions instead of `pumpAndSettle` | The dashboard's shimmer animates until data arrives, so the tree never settles | None |
| 33 | Transfer validators are real domain code mirroring backend API-06, with no balance check | They are graded by TST-02; the client must not pre-reject for insufficient balance (TRF-08), so the 409 path stays testable | A user can submit an amount the backend will reject |
| 34 | The amount must be plain digits with an optional dot (no commas, sign or exponent) | Matches what the backend accepts and keeps the rule to one regex; `double.tryParse` alone would accept `1e3` | Typing `1,500` shows an error; the reference screenshot shows grouped digits |
| 35 | Send money hands back a `TransferDraft` of trimmed strings, remarks null when empty | Turning text into a number for the request belongs to the data layer; the screen stays formatting-free | Conversion happens later, in one place |
| 36 | Phone-kind text fields type in Space Mono (`monoInput`) | DESIGN.md's rule puts phone numbers in mono, and the reference shows mono digits | One-line change to the T1 text field |
| 37 | Pushed screens go back with `canPop ? pop : go(dashboard)` | A screen opened directly (no history) would otherwise have nothing to pop | None |
| 38 | Confirmation's BALANCE AFTER row is optional, only ever a backend-supplied value, and hidden when absent | The mock shows it, but filling it means computing `available - amount` in the app, which rule 1 forbids; the backend has no preview endpoint | The row is not shown until the backend offers one |
| 39 | Request key shown in full on confirmation (the mock shortens it) | It is the Idempotency-Key; showing it whole lets it be matched against backend logs in the demo | Small mono text, ellipsised on narrow screens |
| 40 | Confirmation is stateless: Confirm is disabled while `isSubmitting`, and Edit, back arrow and system back are inert | One attempt, one request (TRF-05); same-frame double taps are dropped by `droppable()` in TransferBloc, as the skill file pairs them | Relies on the bloc for same-frame taps |
| 41 | `/transfer/confirm` stays a placeholder until TransferBloc exists | Its data is the draft plus a request key the bloc generates; the skill file allows route `extra` only between confirmation and result | The send-money flow dead-ends at a placeholder until the data slice |
| 42 | Result screen takes a sealed `TransferResultView` (succeeded / failed) and switches on it | One screen class for both outcomes, as T7 requires, with the compiler checking both branches | None |
| 43 | Failure subtitle is supplied by the caller; "Your wallet was not debited" is only the default | That sentence is true for a server error (e.g. 409) but not after a timeout, where the outcome is unknown | The caller must pick the right copy per failure type |
| 44 | `DetailCard` gained an optional `header` (the failure banner) | The banner sits inside the card border per DESIGN.md; a header slot keeps one card widget instead of a second card | One extra parameter on a T1 widget |
| 45 | System back on the result screen goes to the dashboard | Going back to confirmation after a finished attempt invites a duplicate send | None |
| 46 | `/transfer/result` receives its outcome via route `extra`; opened directly it shows the placeholder | The skill file allows `extra` only on this hop; there is no id to refetch a result by | A deep link to the result screen shows nothing useful |
| 47 | History sorting, search, filter, grouping and date headers live in one pure function, `groupHistory` | Keeps all logic out of `build`, is unit-tested directly, and TransactionsBloc can call the same function later | None |
| 48 | The screen recomputes groups only when data, query or filter change, and stores the result in state | `build` just renders the stored groups; typing re-filters immediately | No debounce yet; the bloc adds `restartable()`/debounce in the data slice |
| 49 | "No matching transactions" is a separate empty state from "No transactions yet" | TXN-04 requires distinct messages for an empty wallet and an over-narrow filter | None |
| 50 | `TransactionRowData.dateLabel` renamed `metaLabel` | History rows show the type (DEBIT/CREDIT) in that slot, dashboard rows show the date; the old name was wrong for one of them | Touched a T1 widget and two test files |
| 51 | Top bar, search and pills stay fixed; only the grouped list scrolls, via an outer `ListView.builder` over day groups | Search stays reachable on long lists, and the list is lazy at the group level as decision 16 planned | Each day's rail is shrink-wrapped (fine for a day's rows) |
| 52 | Details labels the counterparty BENEFICIARY for a debit and SENDER for a credit | TXN-07 says "beneficiary/sender"; on a credit the other party sent the money | Differs from the single label in the mock |
| 53 | Bordered, clipped containers (`DetailCard`, its shimmer, the text-field frame) paint their border as a `foregroundDecoration` | Found in the T9 render: a border painted behind filled content (white rows, the surface row, the `+91` box) loses its curve at the rounded corners | Content now runs to the card edge; the border overlays its outer pixel |
| 54 | The details hero amount sits in a fixed one-line slot, like the balance panel | `FittedBox` shrinks height along with width for long amounts, which moved the card when details arrived; a test now pins the card's position across loading and loaded | None |
| 55 | The details loading pill is the real pill outline with a shimmering dot and label | A plain shimmer block of a guessed height was 3px off the real pill | None |
| 56 | `main.dart` runs `JWalletApp`: theme plus `MaterialApp.router`, router created once in `initState` | Building the router in `build` would reset navigation on every rebuild | None |
| 57 | Until the auth slice, any login input that passes validation signs in (TEMPORARY, in `main.dart`) | Lets all screens be walked end to end now; `createAppRouter` takes `onLoginSubmitted`, which AuthBloc will own | Credentials are not checked in this interim build |
| 58 | Send money → Confirmation passes a `TransferAttempt` (draft plus request key) as route `extra`; the key is made on the push | The skill file reserves `extra` for confirmation → result, but there is no TransferBloc yet; making the key in the confirm builder would change it on every rebuild (a test pins this) | Second use of `extra`; moves into TransferBloc in the data slice |
| 59 | `ConfirmationView.fromDraft` formats the amount with Indian grouping (`₹1,500.00`) and adds `+91` | One place turns a draft into display values; the amount is parsed only for display | None |
| 60 | Fake repositories feed the screens through one TEMPORARY file, `core/router/temporary_fake_wiring.dart` (`FakeData`, per-screen `Fake*` wrappers, entity-to-view converters) | Lets the whole app be walked with sample data before the backend exists, and keeps every piece of sample-data plumbing in one deletable file | Sample data in the app breaks rule 2 / NFR-01 until the data slice deletes this file and the fake repositories; it must not ship |
| 61 | Fake answers are delayed by differing amounts (profile 0.35s, balance 0.7s, list 1.1s; tests use zero) | Makes shimmer and independent section loading visible in the running app | None |
| 62 | Confirm → result uses `go`, not `push` | The finished attempt leaves the back stack, so back can never return to confirmation and resend | None |
| 63 | The fake transfer result's id now points at an existing fake transaction (TXN10006) | "View transaction" opens real details instead of a not-found error | The fake result is fixed: it always reports ₹1,500.00 and the same balance, whatever amount is entered |
| 64 | Seed `TXN10001`–`TXN10012`; new transfer ids continue at `TXN10013` | Fixes a contradiction: next id `TXN10008` implied 7 seeds, but API-05 needs at least 10 | None |
| 65 | Starting balance ₹25,450.75, stored as `2545075` paise | B5's concurrency test is written against it; integer paise never drift | The app's sample data shows a different figure until the data slice deletes it |
| 66 | `seed.json` stores money as `amountPaise` / `balancePaise` | No float ever enters the store, not even at load | The seed is slightly less readable by eye |
| 67 | `createStore()` returns a fresh deep copy and `createApp({ store })` takes it as an argument | Each test starts from the seed with no reset step; the server builds one at boot | None |
| 68 | One error handler writes every error body; anything that is not an `AppError` becomes 500 `INTERNAL_ERROR`, with the stack logged and never sent | API-14 in one place | None |
| 69 | Provisional until answered: error codes `NOT_FOUND`, `INTERNAL_ERROR`, `VALIDATION_ERROR` (also for malformed JSON), `UNAUTHORIZED`, `TRANSACTION_NOT_FOUND`, `IDEMPOTENCY_KEY_REQUIRED`; field errors in `error.fields` as a map | The spec names only three codes; B0 needs the 404 and 500 ones now | Renaming later touches the handler, the OpenAPI file and the tests |
| 70 | Provisional until answered: transaction shape `{id, type, status, amount, currency, counterpartyName, mobileNumber, remarks, createdAt}`, with `id` as the unique reference and `createdAt` also on the transfer response | `seed.json` and the OpenAPI file need a shape now; the Result screen shows the date | Same as above |
| 71 | `npm test` runs `node --test` with no path | Node 22+ treats `node --test test/` as a file named `test` and fails; the bare form finds `*.test.js` on Node 20 and up | Any `*.test.js` outside `node_modules` is picked up |
| 72 | The demo password sits in plain text in `seed.json` | It's a mock with one hard-coded user; hashing would add code without making anything safer | Not how a real server stores passwords; noted as a limitation |
| 73 | Login email is trimmed and matched case-insensitively; the password is matched exactly | Emails aren't case-sensitive in practice; passwords are | None |
| 74 | Wrong password and unknown email return the identical 401 body | Doesn't reveal which accounts exist | None |
| 75 | A missing, blank or non-string email/password is a 400 `VALIDATION_ERROR` naming each bad field, checked before credentials | Lets the app show field errors; matches the 400 shape used everywhere | None |
| 76 | The auth middleware compares the whole header to `Bearer mock_access_token_123`, exactly | Row 3: only that value is accepted; one string comparison is easy to explain | A lowercase `bearer` scheme is rejected, though HTTP treats the scheme case-insensitively |
| 77 | Every user response goes through `toUserResponse`, which picks `id`, `name`, `email` | The password can never leak through a new route by accident | None |
| 78 | A password of only spaces is a 400 (`password` named in `fields`), not a 401 | Same rule as email: blank counts as missing, and a blank password can never be correct, so checking credentials would be pointless | A caller can tell "blank" from "wrong", which reveals nothing about the account |
| 79 | Any body express.json() refuses (over 100kb, unknown charset or encoding) is 400 `VALIDATION_ERROR` "Request body could not be read", not 413/415 | Keeps to the contract's status list, where 400 means bad request data and 500 means a server bug; they were falling through to 500 | Less precise than 413/415 |
| 80 | Paise become rupees in one function, `toRupees` (`paise / 100`), used only when a response is built | An integer divided by 100 always prints with at most 2 decimals, so there's no rounding step and no float in the store | `1500.00` is sent as `1500`; the app formats it (row 2 of the backend decisions) |
| 81 | Each response is built field by field (`toWalletResponse`, `toTransactionResponse`), never by spreading the stored object | Internal fields like `balancePaise` and `amountPaise` can't leak, and the response shape is readable in one place | A new field must be added to the mapper as well as the seed |
| 82 | `GET /transactions` returns the store's array as is; it doesn't sort per request | The store is sorted once at load, and B3 will prepend new transfers, so it stays newest first | If anything ever inserts out of order, the list is wrong; the B3 tests guard the prepend |
| 83 | Transaction ids are matched exactly (`txn10001` is 404) | Ids are opaque strings the server made; normalising them would be a rule nobody asked for | None |
| 84 | `requireAuth` guards the whole `/wallet` and `/transactions` routers, not each route | A protected route can't be added there without auth by forgetting it | An unknown path under them without a token is 401, not 404 |
| 85 | `toRupees` throws unless given a safe integer | Its "at most 2 decimals" promise only holds for integers; a rounding bug in a later task now fails loudly as a 500 instead of sending `0.005` or `null` | None |
| 86 | Any other 4xx raised before our code runs (e.g. a malformed `%` escape in the URL) is 400 `VALIDATION_ERROR` "Invalid request"; only express.json() errors (tagged with `type`) say "Request body could not be read" | The message must not blame a body the request didn't have | One generic message for every non-body case |
| 87 | ETag is switched off (`app.set('etag', false)`) | Every response is live data; Express's default ETag could answer a repeat balance read with an empty 304 | Clients can't use conditional requests; there's nothing worth caching |
| 88 | Permissive CORS in a small middleware of our own, placed before auth: `*` origin, GET/POST/OPTIONS, the Authorization, Content-Type and Idempotency-Key headers; OPTIONS answered 204 | Implements backend decision 17. A preflight carries no token, so it must be answered before auth. A few lines are easier to explain than the `cors` package | Any website can call the mock; fine for a local demo server |
| 89 | Amount check: a JSON number > 0 whose shortest printed form has at most 2 decimals, then `Math.round(amount × 100)` paise, which must be a safe integer | String form catches `1.005` (which ×100 would round to a valid-looking 100) and `1e-7`; once ≤ 2 decimals is proven, rounding ×100 is exact | A numeric string like `"1500"` is rejected (provisional, pending question 11) |
| 90 | Mobile must be a string matching `^[0-9]{10}$`; a JSON number is rejected | A number would lose leading zeros and isn't what the contract shows | None |
| 91 | Beneficiary name and remarks are trimmed and stored trimmed; blank remarks, `null` and absent are all stored as `null`; the 100-char cap applies after trimming | One rule for "no remarks"; whitespace isn't content (provisional, pending question 12) | None |
| 92 | Every invalid field is reported in one 400, and validation runs before the balance check | The app can show all field errors at once; a bad amount is a 400 even when it's also too big | None |
| 93 | `performTransfer` is one synchronous function: check, deduct, record, with no `await` anywhere in it | Node can't interleave two requests inside it, so check-and-deduct is atomic (API-12) without a lock | Any future async step must go before or after it, never inside |
| 94 | New ids are one above the highest existing numeric suffix, computed from the list | No separate counter to keep in sync; it can never reuse an id | O(n) per transfer; irrelevant at this size |
| 95 | B3 didn't check the `Idempotency-Key` header; every B3 test already sent a fresh one | The task said to stub it until B4; the tests didn't need changing then | Superseded by B4 (row 107) |
| 96 | `performTransfer` builds the whole transaction before touching the store; the deduction and the prepend are its last two lines | Neither of those can throw, so any failure earlier leaves balance and history untouched: money can never move without a record | None |
| 97 | `nextTransactionId` finds the highest id with a plain loop, not `Math.max(...list)` | Spreading a very large array into a call overflows the stack | None |
| 98 | The remarks cap counts characters (`[...text].length`), not UTF-16 units | An emoji is one character but `.length` 2; this matches OpenAPI's `maxLength` and what a user sees | Combined characters (an accent typed as letter + mark) still count as two |
| 99 | OpenAPI states "at most 2 decimal places" in words instead of `multipleOf: 0.01` | Validators that check `multipleOf` with float division wrongly reject valid amounts like 0.07 (0.07 / 0.01 = 7.000000000000001) | A tool can't enforce the rule from the schema |
| 100 | Known limit: a JSON number with more decimals that parses to a 2-decimal float (`1.0000000000000001` → `1`) is accepted as that float | Once parsed, the extra digits are gone; telling them apart would mean parsing the raw body text by hand | That one odd input is treated as ₹1.00 |
| 101 | The beneficiary name has no length cap, and a name made only of invisible characters (e.g. a zero-width space) passes; `.trim()` rejects ordinary, non-breaking and ideographic spaces | The spec says only "required"; backend decisions 14–15 say not to invent rules | A huge or invisible name is stored as sent (the 100kb body limit still applies) |
| 102 | The "list stays newest first" test assumes the machine clock is later than the newest seed (2026-11-17T09:02Z) | Transfers are stamped with the real time; faking the clock would add machinery to every transfer test | On a machine with a clock before that date the test would fail |
| 103 | Only a successful transfer stores its key; a 400 or 409 leaves the key free | No money moved, so there is nothing to protect, and a corrected retry with the same key just works (provisional, pending question 8) | Retrying an insufficient-balance request re-checks it instead of replaying the old 409 |
| 104 | No "reserve then release" step and no "in progress" state for a key | The route is synchronous from the key lookup to `remember`, so Node can't start a second request with that key in between; storing on success behaves exactly like reserve-then-release, with less code | Any future `await` inside that block would reopen the gap, and in Express 4 an `async` handler's errors never reach the error handler. B6's delay must come after `remember` and must not make the handler `async` |
| 105 | "Same payload" is the four transfer fields as sent, in a fixed order, as a JSON string; key order and extra fields are ignored; remarks absent/null/empty count as equal | Readable and exact, with no hashing step; values are compared as sent, so `" Rahul"` and `"Rahul"` differ (provisional, pending question 7) | A retry that only changes spacing gets a 409 |
| 106 | A replay returns the stored response exactly, including the balance at that time | API-10 says "the original response"; the app shows the balance right after its own transfer | The replayed balance can be older than the live one |
| 107 | Missing or blank `Idempotency-Key` is 400 `IDEMPOTENCY_KEY_REQUIRED`, checked after auth and before the body; any non-blank value is accepted as a key | The app always sends a UUID; demanding that format would be a rule the spec doesn't ask for (provisional, pending question 6) | Keys are global, not per user; there is only one user |
| 108 | Keys are kept in memory for the life of the process, with no expiry | Matches the in-memory store, which also resets on restart | Memory grows with each successful transfer; irrelevant for a demo |
| 109 | One `isNoRemarks` rule (absent, null, empty, spaces-only) shared by validation and the payload comparison | Two transfers that would store the same record must count as the same payload | None |
| 110 | An `Idempotency-Key` containing a comma is 400 `IDEMPOTENCY_KEY_REQUIRED` | Node joins a repeated header into "a, b", which would otherwise be a brand-new key and deduct again; a UUID never contains a comma | A client can't use commas in its own keys |
| 111 | A used key is checked before the body, so a different payload is 409 `IDEMPOTENCY_KEY_REUSED` even when it is also invalid | The key conflict is the more basic error; the app should never send it in normal use | The caller doesn't learn about its field errors until it uses a new key |
| 112 | Known gap, unreachable today: if building the response threw after the deduction, the key would not be stored and a retry could deduct again | `toTransferResponse` only fails on non-integer paise, which validation rules out (rows 85, 89) | Relies on validation staying in front of `performTransfer` |
| 113 | Left as is: a key over Node's header limit gets Node's bare 431 (not our error shape); two Unicode encodings of the same name count as different payloads | Both happen before or outside our code, and neither occurs with the real app | None |
| 114 | B5 needed no new production code: integer paise (B0–B3) and the synchronous check-and-deduct and key handling (B3–B4) already met it; B5 adds `test/concurrency.test.js` only | Writing code B5 doesn't need would be churn | None |
| 115 | The concurrency tests run one real HTTP server (`app.listen(0)`) and fire requests with `fetch` + `Promise.all`; each test swaps a fresh store into `app.locals` | supertest's one-request helper is not real parallel traffic; one server for the file keeps the 1000-transfer test fast | Tests in that file share a server, so they must not run in parallel with each other (node:test runs them in order) |
| 116 | The B5 tests were checked against three deliberately broken copies (an `await` inside the transfer, an `await` between the key lookup and `remember`, float rupee arithmetic); each break fails at least one test | Tests that never failed prove nothing | Corrected after the B5 critic pass: the 10 × ₹5,000 test first missed a one-tick `await` because, as the first test on fresh connections, its requests reached the server one at a time (TCP handshakes staggered them), not because the pause was short. Fixed by row 117; it now catches a one-tick `await`, in the full run and alone |
| 117 | The concurrency file warms up 20 connections in `before()`; every batch afterwards reuses them | Measured by the critic: on fresh connections a batch of 10 arrived one at a time, so the first test proved nothing about concurrency; after the warm-up up to 10 requests are inside the server together | One more setup step to explain |
| 118 | The "balance the wallet passed through" test sends 10 × ₹3,000 (more than the balance) and requires exactly 8 successes and 2 × 409 | The old 8 × ₹3,000 never hit the limit and didn't check every request succeeded | None |
| 119 | Known risk, accepted: if one `fetch` in a batch throws, its siblings can land after the next test's store swap and cause knock-on failures | Only happens after something has already failed; the first failure is still reported | A real failure can show up as several |
| 120 | `?simulateLatencyMs=` is a middleware placed before body parsing that delays `res.json` by setTimeout; routes stay synchronous | The route still runs at once, so a slow transfer has already deducted and stored its key when a client times out, which is the case idempotency exists for. No `async` handler, so errors still reach the error handler (rows 104, B4 critic) | It patches `res.json` for that one request, which needs a sentence of explanation |
| 121 | The delay applies to every JSON response, errors and replays included; plain digits only (`1e3`, `0x10`, `500.0`, `+500` count as 0), capped at 30,000; missing or invalid means 0 | It simulates a slow server, so everything is slow; a retry without the parameter gets the stored answer at once (provisional, pending question 10) | A retry that keeps the parameter is slow too |
| 122 | API-14 is verified by one test per error path (15 paths), checking the exact body keys, a known code, the status that code belongs to, a JSON content type and no stack trace, plus a test that every code is reached | One table of codes and statuses, checked against every path, catches both a wrong shape and a wrong status | The code table in the test must be kept in step with OpenAPI by hand |
| 123 | The Bruno collection is plain `.bru` files with tests; the `local` environment holds the base URL and the fixed token; transfer requests make their own UUID keys in pre-request scripts | Runs in the Bruno app or with `npx @usebruno/cli run -r --env local`, so graders can run it as a regression suite; it was run against a fresh server (18 requests, 20 tests passed) | Its balance assertions expect a freshly started server |
